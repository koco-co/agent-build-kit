# 调研与环境探索

先查明任务和环境的实际情况。除用户已授权实施外，本阶段只做读取、搜索、分析和无副作用验证。

## Phase 1：确认任务边界

1. 确认任务属于本 Skill；不属于时说明转交方向。
2. 判断任务类型：新建通用 Skill、新建项目级 Skill，或审查升级已有 Skill。
3. 从现有输入提取：目标、非目标、目标平台、输入、输出、已知分支、交付位置和用户已做的决策。
4. 记录授权范围。设计确认、文件修改、提交、推送和发布是彼此独立的授权，不相互推定。

## Phase 2：检查环境与现状

对仓库中的 Skill，至少检查：

- 目录布局、命名规则和已有 Skills 的组织方式；
- 平台适配、安装方式和 Frontmatter 契约；
- CLI、脚本、测试、Hooks、模板和公共组件；
- 加载、触发、验证和发布方式；
- 每个 Frontmatter 字段由谁读取、默认值是什么、属于哪个平台；
- 是否有可复用的构建或校验能力。

对项目级 Skill，还要检查：

- 代码架构、技术栈和真实业务流程；
- 构建、测试、发布和 CI 入口；
- 项目规则、知识库和文档；
- 已有 CLI、Lint、格式化、代码生成和校验机制；
- `.agents/scripts/` 是否存在、被谁调用、是否随项目或整体安装包交付；
- Skill 应放置的位置，以及它与项目能力的边界。

对已有 Skill，建立基线：

- 当前输入、输出、路由、工作流和副作用；
- 当前 Frontmatter 是否最小，缺失字段是否影响调用、参数、权限、上下文或环境说明；
- 已被外部依赖的文件、命令或接口；
- 可复现的问题与已有测试；
- 哪些必须兼容，哪些允许重构。

## Phase 3：核对平台契约与同类实现

1. 优先读取目标平台当前官方规范，确认目录、Frontmatter、触发、权限和资源读取方式。
2. 调研同类 Skill、插件或工具，比较路由、澄清、工作流、模板、校验和平台兼容方式。
3. 只借鉴能改善当前设计的机制，不机械复制目录或措辞。
4. 记录外部来源、许可证和实际借鉴点；来源或许可证不清楚的内容不得复制。
5. 用户明确免除竞品调研时，可以跳过第 2 至 4 项，但不能跳过目标环境和平台契约核对。

## Phase 4：输出调研摘要

内部摘要至少包含：

```text
任务类型：
已确认目标：
明确非目标：
目标平台：
现有可复用能力：
现有约束与兼容接口：
同类实现可借鉴点：
外部来源与许可证：
事实：
推断：
未知项：
潜在风险：
```

完成标准：后续关键问题都能追溯到真实未知项，而不是因为没有检查环境才出现。
