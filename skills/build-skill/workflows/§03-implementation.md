# 实现

只在已确认的设计范围内创建或更新 Skill。发现设计依据变化时，停止并回到设计阶段，不自行扩大范围。

## Phase 1：列出本次改动

修改前记录：

- 允许新增、修改、移动和删除的路径；
- 必须保持兼容的接口；
- 预期验证命令；
- 不属于本次范围的内容；
- 需要另行授权的提交、推送、发布或破坏性操作。

## Phase 2：写入口与主流程

1. 先创建或更新 `SKILL.md`。
2. 按 `rules/architecture.md` 选择章节；只保留有实质内容的章节，不凑固定结构。
3. 按已确认的字段矩阵写 Frontmatter；没有依据的可选字段保持省略。
4. `description` 写清“做什么、何时用、何时不用”，并覆盖独立分支；不要只依赖 Claude Code 专属字段承担触发。
5. 复杂细节移到按需读取文件，入口保留完整目标、路由和完成条件。

## Phase 3：按职责补资源

按以下顺序实现，能复用就不新写：

1. 已有 CLI、测试和脚本；
2. 确有共享需求的 `.agents/scripts/`，否则用 Skill 自有 `scripts/`；
3. 固定结构模板；
4. 可直接模仿的高质量示例；
5. 仍无法机械保证的规则；
6. 需要拆分的工作流；
7. 内容、文案或场景审查清单；
8. 只有存在多 Agent 编排时才加 Prompt 模板。

每完成一个资源，立即确认：

- 有明确的读取或执行入口；
- 路径真实存在；
- 与其他文件没有重复的规范源；
- 不含秘密、机器私有绝对路径或无意义占位内容。

脚本默认用 Python 3.9+，优先无第三方依赖；项目已有统一运行时则跟随项目约定。引入依赖时，同时更新或引用项目的依赖声明，并实际运行安装与验证命令。

## Phase 4：内容初审与文案审查

先用 `checklists/content-review.md` 检查正确性和完整性。存在歧义、缺失决策或权限不明时，先修行为设计，不进入润色。

内容通过后用 `checklists/copy-review.md`，需要改写参考时读 `examples/copy-review.example.md`：

- 优化自然度、清晰度、简洁度和术语一致性；
- 删除重复规范和没有作用的句子；
- 不改变触发、流程、范围、权限、失败处理和完成条件；
- 无法确定原意时退回内容审查，不自行猜测。

文案修改后重跑受影响的内容检查和静态检查。

## Phase 5：项目级接入

项目级 Skill 优先遵循目标项目：

- 复用现有 CLI 和测试入口；
- 使用项目已有配置与目录；
- 不在 Skill 内复制业务实现；
- 两个及以上 Skills 确有共用需求时，才把稳定脚本放进 `.agents/scripts/`，并确认该目录随项目交付；
- 独立安装或发布不能携带 `.agents/scripts/` 时，脚本保留在 Skill 的 `scripts/`；
- Hooks 放在项目规定的位置；
- Skill 只描述模型需要的路由、判断和编排；
- 稳定接口变化时提供迁移或兼容方案。

## Phase 6：平台适配

- 核心正文保持一致；
- 平台专属 Frontmatter、UI 元数据、策略和安装路径集中管理；
- 适配过程可重复、可测试；
- 不手工维护两份内容相同的 Skill；
- 平台不支持的能力要降级或明确标记，不伪造等价行为。

## Phase 7：实施自检

进入正式验证前确认：

- 已确认的每个目标都有对应文件或行为；
- 新文件都有实际用途，没有空目录、空文件、失效引用和重复规则；
- Frontmatter 与字段矩阵一致，Codex 副本不会保留 Claude Code 专属字段；
- 内容和文案审查已完成，文案修改后的回归没有新增问题；
- 变更没有越过用户确认范围；
- 未经授权的提交、推送或发布尚未发生。
