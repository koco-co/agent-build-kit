# 设计与必要确认

把调研结论和已知决策变成可实施的设计。明确的创建、升级或重构请求可以直接进入实施；只有用户要求先评审，或仍有会改变结构、行为、权限或验收的选择时，才保持只读并确认。

## Phase 1：筛出真正需要确认的决策

把信息分成三类：

| 类别 | 处理方式 |
| --- | --- |
| 用户已经说明 | 直接采用，不重复询问 |
| 可从代码、文档或环境查明 | 自行调查，不询问用户 |
| 无法查明且会改变结果 | 进入待确认决策 |

一个问题只有同时满足以下条件才提出：

1. 当前环境无法给出可靠答案；
2. 用户此前没有说明；
3. 至少两个合理答案会导致不同的实现或验收。

不要询问偏好影响很小、可以采用安全默认值，或不会改变交付结果的问题。每轮只问一个主要问题，给出推荐答案和影响：

```markdown
### 问题 N：<需要用户决定的事项>

**推荐：** <推荐答案>

**为什么影响设计：** <会改变哪些目录、行为、产物或验收。>

**推荐理由：** <结合已查明事实。>

**其他选择：** <每个选择的影响。>
```

用户回答后更新决策矩阵，检查是否顺带解决了后续问题，不重复询问已覆盖内容。

## Phase 2：定义行为契约

设计必须说明：

- **Outcome**：一句话结果；
- **Routing**：独立输入分支，以及不属于本 Skill 的处理；
- **Inputs / Outputs**：每个分支需要什么，产物、格式、命名和位置；
- **Workflow**：阶段、分支、失败路径和完成条件；
- **Side effects**：会修改什么，哪些操作需要另行授权；
- **Guardrails**：数据、权限、接口和范围边界；
- **Acceptance**：机械检查、内容审查、文案审查和真实验收。

## Phase 3：设计 Frontmatter 与最小目录

完整读取 `rules/frontmatter.md`，只记录必填字段、拟新增或保留的可选字段，以及用户明确要求审查的字段：

| 字段或配置 | 是否添加 | 目标平台 | 依据 |
| --- | --- | --- | --- |
| `name` | 是 | 通用 | 必填 |

没有触发特征的字段不进入矩阵。目录按职责选择，规则见 `rules/architecture.md`；需要比较粒度时，读取 `examples/global-skill.example.md` 或 `examples/project-skill.example.md`，只借鉴职责边界，不照搬目录。

每新增一个文件，回答：

1. 它解决什么独立问题？
2. 何时读取或执行？
3. 为什么不能合并到现有文件？
4. 如何验证它有用？
5. 谁是这条规则或结构的唯一规范源？

回答不了，就不创建。

## Phase 4：画出按需读取关系

用表格说明何时读取什么：

| 条件 | 读取或执行 | 用途 | 完成信号 |
| --- | --- | --- | --- |
| 输入属于分支 A | `workflows/a.md` | 执行 A 流程 | A 产物通过检查 |
| 生成固定产物 | `templates/x.template.md` | 固定结构 | 必填字段齐全 |
| 需要参考写法 | `examples/x.example.md` | 模仿粒度与风格 | 内容与文案审查通过 |
| 完成实现 | `scripts/validate.py` | 机械检查 | 退出码为 0 |

禁止默认一次性读取全部附属文件。

## Phase 5：划分能力位置与平台适配

按可靠性放置能力：

- 仓库已有 CLI 能完成：复用 CLI；
- 多个 Skills 共用稳定契约且共享目录会随目标交付：`.agents/scripts/`；
- 单 Skill 自用，或无法保证共享目录存在：Skill 自有 `scripts/`；
- 每次事件都必须自动发生：Hooks 或 CI；
- 固定输出结构：模板；输出写法：示例；复杂判断：工作流；无法机械判断的约束：规则或清单。

平台适配遵循 `rules/platform-compatibility.md`：保留一份平台中立的核心工作流，只为真实差异增加适配层，不把一个平台的专属字段假定为另一个平台支持。明确哪些平台能真实运行验证，哪些只能静态检查。

## Phase 6：设计审查与确认方式

明确：

- 内容审查用 `checklists/content-review.md`；
- 文案审查用 `checklists/copy-review.md`，需要示范时读 `examples/copy-review.example.md`；
- 文案修改后的内容回归范围；
- 是否属于必须调用独立 Reviewer 的重要变更；
- 无法调用独立 Agent 时如何记录降级。

需要展示设计时，用 `templates/design-proposal.template.md` 汇总行为、字段、目录、读取关系、能力边界、平台、审查、实施范围、验收和风险；不在本阶段再维护一份字段清单。用户要求先看设计时，展示一次并只提出一次实施确认；存在未决选择时说明差异和推荐方案；范围明确且无未决选择时直接进入实现。
