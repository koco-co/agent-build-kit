# README 验证与交付

机械检查、项目检查、渲染检查和语义验收不能互相替代。

## 机械检查

```bash
python3 <skill-dir>/scripts/validate_readme.py <target-readme> --project-root <project-root> --strict
```

对每个新增或修改的 README（根 README 或伴随 README）分别运行；`--project-root` 始终指向仓库根。只在用户已授权联网时加 `--verify-remote`；远程失败要显示具体 URL。

## 项目检查

运行项目已有且与文档相关的格式化、Markdown Lint、链接检查或测试。不要为了 README 验收临时安装依赖。

检查 `git diff --check`，再审阅完整 README Diff，确认没有覆盖并行工作或改动项目代码。

## 渲染与视觉检查

- 项目已有 Mermaid CLI 时实际解析图表；没有时不临时安装，改用可用的 GitHub 渲染路径，或标记 Mermaid 真实渲染未验证。
- 只有预览已批准外部传输且当前环境具备渲染 API 凭据时，才可调用渲染 API 检查 GFM HTML。
- 所有新增或修改图片都要实际查看：浅色与深色背景、裁切、可读性和替代文本。
- 验证 Shields、远程图片和外部链接时记录访问时间与结果。

API 返回 HTML 只证明 Markdown 转换成功；没有在 GitHub 仓库页面查看时，不得声称 GitHub 页面视觉验收已完成。

## 语义验收

使用 `checklists/semantic-acceptance.md`，确认：

- 项目定位和功能准确；
- 安装与快速开始构成最短成功路径；
- 图表比文字更清楚；
- 视觉样式保持内容清晰易读；
- 限制、许可证和未验证项诚实。

发现失败时修复并重跑受影响检查。所有检查都要有结果；未运行项要有明确原因。

## 交付

结果优先，保持紧凑，但用户应能复验。

```markdown
## 完成情况

- 目标：
- 已完成：
- 明确未处理：

## README 内容

- 最终章节：
- 视觉组件：
- 同步文件：
- 新增资源：

## 验证

| 状态 | 命令或场景 | 结果 | 说明 |
| --- | --- | --- | --- |

## 失败与修复

- 无 / <失败、原因、修复和重跑结果>

## 剩余边界

- 未验证：
- 阻塞：
```

使用文件链接定位最终 README、伴随 README、图片和 SVG。明确说明是否生成图片、是否访问远程服务，以及是否完成真实 GitHub 页面视觉检查。

不要把提交、推送、Release、GitHub 社交预览配置或仓库主页设置列为已完成，除非用户另行授权且实际执行。
