# 修复与复检

## Phase 1：记录已确认的修复范围

记录用户确认修复的问题编号。用户确认全部时处理完整报告；只确认部分时只处理明确编号，其余保持不变并在交付中列出。用户一开始就明确要求“检查并修复”时，报告范围内无需新决策的成立问题视为已确认；需要新增范围、新决策或领域正文确认时暂停。

修复确认授权报告中的文件改动和验证，不授权 commit、push、发布、部署、外部写入或本地 Plugin 更新。

## Phase 2：由对应领域的 Skill 修复

按问题主领域调用对应 Skill 的修复分支，并传递：问题、证据、确认范围、影响文件、验证方式、工作区保护要求和本次健康检查任务的提交限制。

领域 Skill 直接修复已经完整确认且不含新决策的内容。需要新增或整体替换 README、AGENTS.md / CLAUDE.md，或决定新的产品行为、公开契约和 Skill / Plugin 行为时，先执行该领域已有的内容确认；不得用健康检查的概括性修复确认替代用户尚未看过的正文或行为。

## Phase 3：领域验证

每个修复完成后运行报告中承诺的验证方式和领域现有严格校验。失败时在已确认范围内修复并重跑；若修复需要新增范围或决策，暂停并向用户说明。

记录实际命令、退出状态、关键结果和未运行原因。文件存在、校验器发现或安装成功不代替真实平台与产品行为验证。

## Phase 4：重新运行健康检查

领域验证完成后，以同一范围重新运行健康检查。复检必须确认：

- 已确认问题不再出现；
- 修复没有造成新的领域问题；
- 未确认问题仍准确保留；
- 无法完成的真实客户端或外部验证仍标记为未验证。
