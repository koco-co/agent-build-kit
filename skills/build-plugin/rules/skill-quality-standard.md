# Skill 质量标准

## 最小充分与最高优先级

所有内容遵循最小充分原则：只保留能改变理解、执行或验收的内容。


行为、分支、兜底、兼容、校验、权限控制和提示词，都必须以用户需求、仓库事实、可复现缺陷、平台契约或明确安全要求为依据；说不出具体依据就删除。必要的输入校验、数据安全、权限边界和错误处理仍需保留，并写明依据。

## 1. 把工作放在最可靠的位置

按可靠性从高到低选择：仓库已有 CLI/工具 → 可随目标交付的共享脚本 → Skill 自有脚本与测试 → 模板 → 示例 → 规则 → 说明性提示词。

- 确定性行为交给脚本或 CLI，不在提示词里重复堆规则。
- 固定输出结构用模板；容易误解的结果用示例；简单约束用规则。
- 只有至少两个 Skills 共享稳定契约、且 `.agents/scripts/` 会随目标交付时才提升为共享脚本；否则保持 Skill 自包含。
- 新脚本优先使用无第三方依赖的 Python 3.9+；项目已有统一运行时则跟随项目约定，并记录可复现命令。

## 2. 单一规范源与渐进式读取

- 每条规则、产物结构和平台行为只保留一处权威定义；其他文件引用，不复制正文。
- `SKILL.md` 只保留目标、路由、步骤和必要红线；结构、字段和资源职责放到对应规则或模板。
- 初始上下文只读 `SKILL.md`；每个附属文件都要有读取条件，按需完整读取，不无理由加载整棵目录。
- 附属文件使用相对 Skill 根目录的引用；项目公共脚本只有在交付能保证 `.agents/scripts/` 存在时才可调用。

## 3. 路由与平台

- `description` 与 Routing 共同说明能力、输入分支、排除条件和退出/转交方式，避免与相邻 Skill 误触发。
- 正文保持平台中立；调用权限和展示信息由 Frontmatter 与 `agents/openai.yaml` 控制，正文不重复配置语义。
- 仅限用户调用的 Skill 不在正文重复说明调用权限；允许模型调用的 Skill 在跨平台 `description` 写清触发条件、排除条件及与相邻 Skill 的边界，不依赖 `when_to_use` 承担唯一触发语义。
- 平台差异确实改变步骤、输出或降级方式时，才保留最小条件分支；不得假定未知字段跨平台可用。
- `compatibility` 只写仍然有效的硬性环境要求，默认省略。

## 4. 决策与确认

- 能自行查明的事实不询问；已知答案不重复询问。
- 只有会改变实现、权限或验收的真实决策才提问；每轮一个主要问题，给出推荐答案和影响。
- 存在未决设计选择时，确认前不写入目标文件；实施确认不自动授权 commit、push、发布或破坏性操作。

## 5. 内容与文案

- 每个步骤写清条件、动作、结果和完成证据；已确认分支和可复现失败要有明确结果。
- 先保证行为正确、完整，再改文案；语义有歧义时回到设计，不让文案审查替设计做决定。
- 文案以准确、自然、简洁为准：一句话说清一件事，术语前后一致，去掉空话、重复和翻译腔；不改变触发、流程、范围、权限、失败处理或验收。
- 删除与脚本、模板、示例、规则或其他规范源重复，或说不清用途的内容；不以固定章节或行数代替判断。

## 6. 审查与验收

- 新建、整体重构，或改变触发、Frontmatter、权限与平台行为时，调用独立 Reviewer；Reviewer 只报告问题，修复后复查受影响项。
- 验收至少区分：结构/引用静态检查、内容与文案审查、文案后的内容回归、适用场景、真实平台运行。不以“文件已生成”或“看起来正确”代替证据。
- 未运行、阻塞、静态通过但未真实运行的内容，如实记录；修复失败项后，重新运行受影响的检查。
- 具体检查顺序和命令放在验证工作流中，本规则不复制清单。

## 7. 升级与迁移

- 先识别稳定接口和外部依赖，只保留已确认仍有调用方依赖的兼容行为。
- 破坏性调整要说明影响、迁移方案和回退方式；不得以“重构”为由删除用户仍在依赖的能力。
- 变更范围必须与用户确认的设计一致；没有依据的兼容、兜底和平台适配不进入实现。
